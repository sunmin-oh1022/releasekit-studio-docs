Reading the producer

Plugin 1.0을 설명하는 네 가지 문장

① 대화가 진입점이다

기획자는 목적을 말하고, Plugin의 스킬은 필요한 문맥을 읽어 질문·작성·검토 순서를 안내한다.

② 파일이 기억이다

대화에서 정한 내용은 문서, ROADMAP, 검토 기록과 `.planning` 계약 파일에 남아 다음 세션의 근거가 된다.

③ Core와 Packs로 범위를 고른다

Core는 공통 뼈대, Pack은 선택 기능이다. 필요한 Pack만 조합한다.

④ Studio를 직접 제어하지 않는다

Plugin은 약속된 프로젝트 파일을 쓰고, Studio는 그 결과를 독립적으로 다시 읽어 판정한다.

1.0에서 확정된 출력 계약

kit.json설치된 킷 버전과 선택 Pack을 기록하는 구성 사실Plugin → Studio
status.json코치가 남긴 현재 브리핑과 다음 행동 문맥Coach → Studio
문서 모델REQ·POL·SCR·FLOW·TC·FEAT의 ID, 상태와 구조Plugin → Project
검증 계약결과 판정과 REVIEW·UX-REVIEW 기록 위치Plugin ↔ Studio
studio-checkStudio 검증 요약을 다음 코치 세션에 전달Studio → Coach

독립 버전

Plugin과 Studio는 각자 버전업한다.

매 릴리스 판정

계약 영향 등급과 근거를 반드시 기록한다.

실물 교차 검증

최종 설치 파일의 해시(내용이 같으면 같은 값이 나오는 디지털 지문)와 실제 프로젝트 흐름을 확인한다.

Plugin 1.0은 제품명과 계약 문서를 확정했지만 기술 식별자 `planning-kit`과 0.8 계열 프로젝트 데이터 계약을 유지했다. 최종 설치본은 ReleaseKit Studio 1.0.0과 호환된다.

Topic 1 · Single source of truth

SSOT 문서는 모든 내용을 한 파일에 모은 문서가 아닙니다

SSOT는 같은 사실을 여러 곳에 복사하지 않고, 수정할 원본을 하나로 정하는 원칙입니다.

Releasekit의 SSOT는 하나의 거대한 문서가 아니라, 역할별 원본 문서가 ID로 연결된 기획 시스템입니다.
WHY & RULE의도와 정책PRD · POL · DECISIONS왜 만드는가, 어떤 규칙인가
→
AUTHORITATIVE SOURCES행동과 경험의 원본REQ · SCR · FLOW · TCID·상태·출처로 서로 연결
→
DERIVED VIEW개발용 기능 목록FEAT는 원본을 다시 정의하지 않음REQ·POL·SCR·DEC·TC를 참조

문서마다 소유하는 사실이 다릅니다

원본권위 있게 정의하는 것다른 문서가 사용하는 방식
PRD문제, 사용자, 목표와 제품 범위요구사항과 우선순위의 판단 근거
POL비즈니스 규칙, 조건과 예외REQ·화면·테스트가 정책 ID 참조
REQ시스템이 제공해야 할 행동SCR·FLOW·TC·FEAT가 요구사항 ID 참조
SCR / FLOW화면 상태와 사용자 이동요구사항을 실제 경험으로 구체화
TC완료를 확인하는 검증 기준REQ가 구현됐는지 재현 가능한 조건 제공

원본이 바뀌면

참조 문서를 찾아 영향 범위를 확인하고 파생 문서를 다시 생성·검토합니다.

기록과 실측이 다르면

실제 원본 파일이 이깁니다. 이전 기록은 차이를 설명하는 보조 근거로 남습니다.

구분

FEAT는 개발 범위를 묶은 파생 문서입니다. 내용을 복사하지 않고 원본 ID와 버전을 가리킵니다.

Topic 2 · Why Markdown works

Markdown이 작동하는 이유는 가벼워서가 아니라 구조를 공유해서입니다

Markdown은 문장과 구조를 함께 담는 텍스트 형식입니다. 사람·AI·검사기·Git이 같은 원본을 읽을 수 있습니다.

## REQ-AUTH-014 상태: reviewed 정책: POL-AUTH-003 사용자는 만료된 인증을 다시 갱신할 수 있어야 한다. | 예외 | 기대 결과 | | 오프라인 | 재시도 안내 | 검증: TC-AUTH-021
사람이 바로 읽습니다별도 편집기나 데이터베이스가 없어도 리뷰 가능
AI가 문맥으로 읽습니다제목·표·목록·ID가 의미 있는 경계가 됨
스크립트가 판정합니다ID, 상태, 참조와 필수 절을 결정적으로 검사
Git이 변화를 기록합니다이전 버전과의 차이(diff)를 줄 단위로 비교·검토·복구

Markdown을 작동하는 문서로 만드는 네 가지 규약

  • 01안정적인 ID · 제목이 바뀌어도 REQ·POL·SCR·FLOW·TC 식별자는 유지합니다.
  • 02명시적인 상태 · draft → reviewed → approved → implementing → done 순서로 관리합니다.
  • 03정해진 구조 · 헤더·표·체크박스·참조 열의 위치와 의미를 프로젝트 규칙으로 고정합니다.
  • 04출처 연결 · 같은 사실을 복사하지 않고 원본 ID와 파일·줄을 따라가도록 만듭니다.

Studio

표·헤더·파일의 ID를 합치고 출처와 줄 번호를 보존합니다.

check-docs

누락·중복·끊긴 연결과 상태 규칙을 자동 검사합니다.

Git

파일 변경 이력을 저장하는 도구입니다. 누가 어느 문장을 바꿨는지 비교하고 이전 상태로 돌아갈 수 있습니다.

한계

.md 파일이 곧 SSOT는 아닙니다. ID·상태·참조·작성 주체가 합의돼야 합니다.

Topic 3 · Rules, skills & scripts

Plugin은 규칙을 읽고, 스킬로 판단하고, 스크립트로 확인합니다

Rules는 기준, Skills는 대화형 절차, Scripts는 반복 가능한 자동 작업입니다.

REQUEST기획자가 목적을 말함“결제 요구사항을 정리하자”
SKILL작업 절차를 선택질문·읽기·작성·승인 순서 결정
RULES프로젝트 규약 적용ID·상태·문서 경계·완료 조건 준수
SCRIPT결과를 기계 검증누락·연결·형식·빌드 결과 판정

Rules · 선언

“무엇이 올바른가”를 정의합니다. 문서 모델, ID 규칙, 상태 전이, 파일의 쓰기 주체와 검토 조건이 여기에 속합니다.

Skills · 절차

질문과 판단이 필요한 작성·분석·검토 순서를 정합니다.

Scripts · 판정

문서 검사·PDF 생성처럼 결과가 명확한 작업을 반복 실행합니다.

판단과 자동화의 경계

질문담당이유
이 요구사항의 의도가 충분한가?사람 + Skill맥락·우선순위·선택이 필요
REQ ID가 중복됐는가?Script같은 입력이면 답이 항상 같음
초안에서 검토 통과로 언제 바뀌나?Rule팀이 합의한 상태 전이 기준
검토 결과를 원본에 반영할까?사람 승인 + Skill제품 의미를 바꾸는 쓰기 작업

문서 자동 검사기(check-docs)란?

내용의 품질이 아니라 ID·상태·필수 항목·참조 규칙을 자동 확인하는 Script입니다.

① 자동 검사기누락·중복·끊긴 연결·형식 확인→ ② AI 검토내용의 모순·근거·사용성 판단→ ③ 사람 승인제품 결정과 우선순위 확정
검사기의 통과는 기획 품질의 최종 합격이 아니라, AI 검토와 사람 판단을 시작할 최소 구조가 갖춰졌다는 뜻입니다.
Hooks

저장·검토·배포 시점에 Script나 알림을 자동 실행하는 선택 기능입니다.

Topic 4 · Development handoff

개발 핸드오프는 문서 더미가 아니라 기준 시점이 고정된 실행 계약이어야 합니다

핸드오프에는 구현 범위·규칙·완료 조건과 기준 버전이 연결돼야 합니다.

시간의 모호함을 없앱니다

동결본의 파일 해시와 현재 원본을 비교해, 개발이 변경된 명세를 놓쳤는지 또는 명세에 없는 내용을 구현했는지 판정할 근거가 생깁니다.

Topic 5 · Design-to-development handoff

개발에는 문서가 아니라 결정·경험·검증이 연결된 묶음을 전달합니다

핸드오프 문서는 결정·구현·검증을 연결해 개발자의 추측을 줄여야 합니다.

전달 문서개발에서 하는 역할디자인이 개입하는 지점
PRD · POL · DECISIONS범위, 비즈니스 규칙, 예외와 선택의 근거정책을 화면 상태·문구·금지 행동으로 번역
REQ · INDEX구현 단위, 우선순위, API·상태 모델과 추적 ID요구사항이 실제 화면과 사용자 행동으로 성립하는지 확인
IA · SCR · FLOW화면 구조, 이동, 분기와 예외 흐름정보 위계·탐색·상태 전환과 접근성 설계
Designspec · Prototype컴포넌트, 반응형 규칙, 상호작용의 구현 기준선기본·로딩·빈·오류·권한 상태와 시각 토큰을 동결
TC · UX review기능 완료 조건, 회귀 테스트와 인수 기준사용성 기준과 디자인 QA 항목을 검증 조건에 반영
FEAT · 일정개발 범위 합의, 산정·WBS·스프린트 분해FEAT의 기준 화면 버전과 미결 디자인 범위를 확인
용어·라벨 사전코드·화면·분석 이벤트의 이름을 일관되게 사용콘텐츠 디자인과 컴포넌트 문구의 단일 기준 제공

디자인은 핸드오프 전후 세 번 개입합니다

① 구조 설계

IA와 FLOW 단계에서 정보 위계, 주요 여정과 정책 예외가 사용자 경험으로 성립하는지 기획과 함께 결정합니다.

② 경험 기준선 동결

Designspec과 Prototype에 모든 상태·상호작용·반응형·접근성·토큰을 기록하고 도메인 × 버전으로 동결합니다.

③ 구현 검증

개발 결과를 TC와 동결본에 대조해 기능·사용성·시각 차이를 찾고, 변경이 필요하면 새 버전으로 되돌려 보냅니다.

PLANNINGSSOT 확정범위·정책·요구사항·결정 승인
DESIGN경험 기준선화면·흐름·상태·프로토타입 동결
DEVELOPMENT구현과 추적REQ·FEAT ID 기준 코드·테스트 연결
QA & REVIEW기능·디자인 검증TC·UX review·동결본과 결과 대조
디자인은 기획이 끝난 뒤 화면을 꾸미는 후속 단계가 아닙니다. 정책과 요구사항을 경험으로 번역하고, 개발이 따라야 할 시각·행동 기준선을 만들며, 구현 결과의 차이를 다시 판단하는 공동 소유자입니다.
변경 원칙

핸드오프 뒤 디자인이 바뀌면 새 버전을 만들고, 관련 문서의 영향 범위를 기록합니다.

개발 핸드오프 용어를 기획자의 말로 풀면 이렇습니다

용어의 목적은 개발자가 추측하지 않게 만드는 것입니다. 산출물 이름보다 “어떤 질문에 답하는가”를 먼저 확인하세요.

PRD · 제품 정의누구의 어떤 문제를 왜 풀며, 이번 범위에서 무엇을 제외하는가?
POL · 정책허용·제한·계산·권한·예외에 적용할 비즈니스 규칙은 무엇인가?
REQ · 요구사항사용자 또는 시스템이 실제로 할 수 있어야 하는 행동은 무엇인가?
IA · 정보 구조정보와 기능을 어떤 메뉴·화면·위계로 묶고 찾게 할 것인가?
SCR / FLOW · 화면과 흐름각 화면에 무엇이 보이고, 행동 뒤 어디로 이동하며 예외 때 어떻게 되는가?
TC · 테스트 조건어떤 입력과 행동에서 어떤 결과가 나오면 구현 완료라고 판단하는가?
FEAT · 개발 기능 묶음이번 개발 단위가 참조하는 요구사항·화면·정책·테스트는 무엇인가?
API · 시스템 연결 규칙화면과 서버가 어떤 데이터를 어떤 형식으로 주고받는가?
컴포넌트 · 재사용 UI버튼·입력창처럼 여러 화면에서 같은 규칙으로 반복 사용하는 화면 조각
디자인 토큰색·간격·글자 크기처럼 디자인 값을 이름으로 정해 일관되게 쓰는 기준
QA · 품질 확인구현 결과가 요구사항·화면·테스트 조건과 같은지 확인하는 활동
WBS / 스프린트일을 작은 작업으로 나눈 계획 / 정해진 기간에 실행할 작업 묶음
manifest · 인계 목록표어떤 파일의 어느 버전을 넘겼는지 한눈에 확인하는 목차 겸 영수증
hash · 디지털 지문파일 내용이 달라지면 값도 바뀌어 동결 이후 변경 여부를 확인하는 값
읽는 순서

왜(PRD·POL) → 무엇을(REQ·FEAT) → 어떻게(IA·SCR·FLOW) → 완료 기준(TC·QA) 순으로 읽습니다.
