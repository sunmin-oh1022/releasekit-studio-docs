Part 1 · Why version control

형상관리의 중요성

기획서_최종_최종_진짜최종_v3.pptx를 놀리는 농담은 다들 하지만, 진짜 손해는 다른 데서 납니다. 파일은 어떻게든 찾습니다. 못 찾는 건 왜 그렇게 바꿨는지입니다.

반년 뒤 누군가 묻습니다. “자동 로그인은 왜 기본 꺼짐이죠?” 아무도 기억하지 못합니다. 당시 슬랙 스레드는 밀려났고 결정한 사람은 다른 팀으로 갔습니다. 그래서 팀은 같은 논의를 다시 합니다. 이게 실제 비용입니다.

형상관리는 파일을 정리하는 기술이 아니라, 결정의 이유를 잃지 않는 기술입니다.

기획자에게 중요한 이유

최신본을 찾는 일보다 더 중요한 것은 결정의 근거를 재사용하는 일입니다. 변경 이력이 남으면 신규 담당자와 개발자, AI가 같은 맥락에서 다음 작업을 시작할 수 있습니다.

Part 2 · Three concepts

먼저 이해할 개념 세 개

Git에는 용어가 많지만 형상관리의 기본은 저장소·커밋·히스토리입니다. 나머지는 이 셋의 응용입니다.

저장소Repository / Repo

프로젝트 하나에 해당하는 폴더. 모든 파일과 지금까지의 변경 이력이 함께 들어 있습니다. 공유 드라이브 폴더에 타임머신이 붙었다고 보면 됩니다.

커밋Commit

저장. 단, 덮어쓰기가 아니라 한 층 쌓기입니다. 저장할 때 메시지를 남기며, 이 한 줄이 나중에 팀을 살립니다.

히스토리History / Log

쌓인 커밋의 목록. 원하는 시점의 문서를 보고 필요하면 되돌릴 수 있습니다. 게임의 세이브 포인트와 같습니다.

Part 3 · Tools

Git · GitHub · GitLab의 차이

Git은 기술이고, GitHub과 GitLab은 그 기술을 웹에서 함께 쓰게 해주는 서비스입니다.

Git기술 · 2005

버전을 관리하는 프로그램 그 자체입니다. 내 컴퓨터 안에서 동작하고 인터넷이 없어도 작동합니다.

GitHub서비스 · Microsoft

Git 저장소를 인터넷에 올려 여럿이 함께 쓰는 서비스입니다. 오픈소스 세계의 사실상 표준입니다.

GitLab서비스 · 우리 회사

GitHub과 하는 일은 거의 같습니다. 회사 서버에 직접 설치해 운영할 수 있어 우리 회사가 사용합니다.

회사가 GitHub이 아니라 GitLab을 주는 이유

GitLab은 자체 서버에서 운영할 수 있습니다(self-hosted). 코드와 문서가 회사 네트워크 밖으로 나가지 않고, 접근 권한과 감사 기록을 회사가 통제합니다. 기획 문서에는 미출시 기능, 매출 수치, 파트너 정보가 들어가므로 팀 지식 저장소로 GitLab이 적합합니다.

GitHub의 Pull Request(PR)와 GitLab의 Merge Request(MR)는 같은 기능입니다.

세 이름을 구분하는 가장 쉬운 법

Git은 변경 이력을 만드는 엔진입니다. GitHub과 GitLab은 그 엔진을 팀이 함께 쓰도록 저장소, 리뷰, 권한, 이슈 화면을 제공하는 협업 공간입니다.

Part 4 · Workflow

개발자가 일하는 순서

“브랜치 따서 작업 중”, “MR 올렸으니 리뷰”, “머지하고 배포”는 모두 아래 흐름입니다.

main · 확정본feature/소셜로그인 · 작업 사본main · 반영 완료
브랜치 만들기branch확정본은 그대로 두고 작업용 사본을 만듭니다. 여러 명이 동시에 다른 사본에서 일할 수 있습니다.
커밋하기commit의미 있는 결정 단위마다 이유를 적고 저장합니다. 한 번에 몰아서 하지 않습니다.
푸시하기push내 컴퓨터의 커밋을 GitLab 서버로 올립니다. 웹에서 편집하면 커밋과 푸시가 함께 일어납니다.
MR 만들기merge request“작업 사본의 변경을 확정본에 반영해 주세요”라고 요청하고 리뷰어와 이유를 적습니다.
리뷰하기review바뀐 줄에 직접 댓글을 답니다. “3페이지 두 번째 문단”이라고 설명할 필요가 없습니다.
머지하기merge승인 후 사본의 변경을 확정본에 합칩니다. 이 순간이 반영 완료입니다.
충돌

두 사람이 같은 줄을 다르게 고치면 시스템이 어느 쪽이 맞는지 사람에게 선택을 요청합니다. 사고가 아니라 판단 요청입니다.

Part 5 · GitLab web workflow

브라우저에서 GitLab 작업을 따라갑니다

터미널이나 별도 프로그램 없이 GitLab 웹 화면에서 저장소 생성부터 리뷰와 반영까지 진행합니다.

저장소 만들기우상단 + → New project → Create blank project. 이름은 planning-wiki-본인이름. Internal 또는 Private을 선택하고 README 초기화를 체크합니다.
확정본에 커밋README.md의 Edit single file에서 팀 소개를 씁니다. 메시지에 “저장소 소개 문구 추가”라고 쓰고 커밋합니다.
히스토리와 diff 확인Code → Commits에서 방금 커밋을 엽니다. 추가된 줄과 삭제된 줄을 색으로 확인합니다.
브랜치에서 새 문서 작성+ → New file. decisions/2026-08-23-첫-팀회의.md를 만들고 커밋할 때 Create a new branch를 선택합니다.
MR 올리기Create merge request를 누릅니다. 왜 문서를 추가했는지 쓰고 Reviewer를 지정합니다.
리뷰하고 머지MR의 Changes 탭을 열어 바뀐 줄에 댓글을 달고 Merge를 누릅니다. 확정본 반영을 확인합니다.
웹에서 직접 편집하면 커밋과 푸시가 한 번에 일어납니다. 핵심은 브랜치에서 작업하고 MR로 합의하는 흐름입니다.
막히면

GitLab 버전에 따라 메뉴 위치와 이름이 다를 수 있습니다. 상단 검색창에 new file, merge request 같은 영문 키워드를 입력하세요.

Part 7 · Working with Claude

Claude를 쓰기 위한 전제

Claude 같은 AI 개발 도구는 파일과 폴더를 통째로 읽고 씁니다. 위키 한 페이지를 복사해 묻는 것과 팀 저장소 전체를 연결하는 것은 다른 일입니다.

저장소가 있으면 가능해지는 질문

“로그인 관련 결정을 모아줘”
“신규 기능이 기존 결정과 충돌하는지 찾아줘”
“팀 용어 사전에 맞춰 표현을 통일해줘”

Plugin과 Skill도 결국 파일

플러그인과 킷도 텍스트 파일 묶음입니다. 저장소에 올리면 팀이 같은 버전을 쓰고, 누가 무엇을 왜 고쳤는지 남습니다.

외우지 않아도 되는 것

git commit -m 같은 명령어는 외울 필요가 없습니다. Claude에게 커밋과 푸시를 요청할 수 있습니다. 다만 브랜치를 만들 상황인지, 지금 머지해도 되는지는 사람이 판단해야 합니다.

환경을 올리는 순서

한 번에 터미널까지 갈 필요는 없습니다. 대부분의 기획자는 STEP 2에서 멈춰도 충분합니다.

STEP 0
GitLab 웹 화면설치 없이 문서 읽기·쓰기, 리뷰, 승인까지 합니다. 팀 전원이 익혀야 합니다.
STEP 1
VS Code + GitLab 연결웹 편집기가 답답해질 때 저장소를 clone하고 버튼으로 커밋·푸시합니다.
STEP 2
Claude Code 붙이기저장소 폴더를 통째로 연결하고 Git 명령은 Claude에게 요청합니다.
STEP 3
터미널에서 직접 · 선택관심 있는 사람만 익힙니다. 직접 하지 않아도 문제없습니다.

Appendix · Glossary

개발 용어 정리

회의에서 자주 들리는 영어 표현과 기획자 관점의 쉬운 뜻입니다.

Repository저장소 · repo프로젝트 파일과 모든 변경 이력이 함께 들어 있는 폴더
Commit커밋 · 저장이유를 적고 변경을 한 층 쌓는 저장
Branch브랜치 · 작업 사본확정본을 건드리지 않고 작업하는 독립 사본
main메인 브랜치 · 확정본팀이 합의한 상태를 유지하는 기준 브랜치
Merge머지 · 병합작업 사본의 변경을 확정본에 합치는 일
Merge RequestMR · 병합 요청GitLab의 리뷰와 승인 요청
Pull RequestPR · 병합 요청GitHub에서 MR을 부르는 이름
Diff디프 · 변경 비교두 시점 사이의 추가와 삭제만 보여주는 화면
Clone클론 · 내려받기서버 저장소 전체를 내 컴퓨터로 복사
Pull풀 · 최신화서버의 최신 변경을 내 컴퓨터로 내려받기
Push푸시 · 올리기내 컴퓨터의 커밋을 서버로 올리기
Checkout체크아웃 · 이동작업할 브랜치를 바꾸는 일
Conflict컨플릭트 · 충돌같은 줄의 서로 다른 변경을 사람이 선택해야 하는 상태
Revert리버트 · 되돌리기기록을 남긴 채 반영된 변경을 취소
Issue이슈 · 할 일논의하거나 처리할 작업 하나
Markdown.md · 마크다운제목과 목록을 기호로 표현하는 텍스트 형식
READMEREADME.md · 안내문저장소 첫 화면에 보이는 사용 안내
명령어보다 먼저 익힐 것은 판단 기준입니다. 어디서 작업하고, 무엇을 기록하고, 언제 리뷰와 승인을 요청할지 이해하면 됩니다.
